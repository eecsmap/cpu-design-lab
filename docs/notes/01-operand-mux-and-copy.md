# 操作数 mux 的自由度,与 CSRRW 的约束

对象:Sodor 1-stage,`rv32_1stage/{dpath,cpath,consts}.scala`

一次从"这些选择是不是任意的"出发的设计空间探索。

> ## ⚠️ 这篇笔记的定量结论已被实测推翻
>
> 下面对代价的分析靠**数 mux 输入个数**,后来把两个变体真的实现出来、过了 Vivado
> 综合与布局布线,结果是:
>
> | 变体 | 纸面预测 | 实测面积 | 实测 Fmax |
> |---|---|---:|---:|
> | A(`imm_u`↔`PC` + COPY2) | 零成本或略差 | **−6.5%** | **+2.5%** |
> | B(CSR 脱离 ALU) | 应该更省 | **+2.5%** | **−2.5%** |
>
> **两个预测都错了,方向还是反的。** 数据和失败原因见
> [measurements/2026-08-30-operand-mux-variants.md](https://github.com/eecsmap/cpu-design-lab/blob/main/measurements/2026-08-30-operand-mux-variants.md)。
>
> 笔记原样保留,因为**推理链条本身仍然有价值**,而且它错在哪里比它对在哪里更值得记。
> 每个被推翻的段落下面都标了实测结果。

定性的结论仍然成立:**大部分选择是任意的,直到 `CSRRW` 出现;而 `CSRRW` 的约束又来自
一个可以被质疑的接口决定。** 错的是对"改动要花多少代价"的估算。

---

## 起点:四个"是不是可以换"

读完 1-stage 的数据通路之后,自然会怀疑那些操作数分配是不是随手定的:

1. `PC` 现在挂在 op2,能不能放 op1?
2. `ALU_COPY1` 能不能换成 `ALU_COPY2`?
3. 各种立即数能不能都挂到 op2?
4. 跳转目标能不能都用 ALU 算,不要那三个专用加法器?

前三个问的是**编码上的自由度**,第四个问的是**结构上的自由度**。这两类问题的答案性质
完全不同,后面会看到。

---

## 第 4 个先出局:结构约束是真的

`br_target` / `jmp_target` / `jump_reg_target` 是三个独立于 ALU 的加法器
(`dpath.scala:189–191`),分支比较也是三个独立的比较器(`dpath.scala:242–244`)。

`JAL` / `JALR` 的目标**技术上可以**交给 ALU —— `JALR` 的译码行 `OP1_RS1, OP2_IMI`
本来就正好是 `rs1 + imm_i`,只是 `alu_fun` 填了 `ALU_X` 没去用它。但这么做会把一条短
路径(纯加法器)合并进一条长路径(带 11 路输出 mux 的 ALU),再串进 PC mux。1 级核的
时钟周期就是最长路径,**这是拿 Fmax 换几十个 LUT,不划算**。

分支则是**根本不行**。一条 `BEQ` 在同一个周期内需要两个算术结果:

- `rs1 == rs2`?决定跳不跳
- `pc + imm_b` —— 跳到哪

一个 ALU 一个周期只能算一次。要么放两个 ALU(那就没省),要么拆成两拍(那就不是 1 级
核了)。所以译码表里 `BEQ` 整行都是 don't care(`OP1_X, OP2_X, ALU_X, WB_X`)—— 分支
指令根本不使用 ALU。

> **同一周期内的并发算术需求数量,决定了你至少需要几个算术部件。** 这个约束在体系结构
> 里反复出现:超标量为什么要多个 ALU、为什么访存地址生成单元(AGU)常常独立于 ALU,
> 都是同一件事的放大版。

结构自由度到此为止。剩下三个问题是纯编码问题,继续。

---

## 第 1 和第 3 个其实是同一个改动

`OP2_PC` 只有 `AUIPC` 一个用户:

```
AUIPC -> List(Y, BR_N, OP1_IMU, OP2_PC, ALU_ADD, WB_ALU, ...)
```

`ALU_ADD` 有交换律,所以 `OP1_PC, OP2_IMU` 等价。而且 `AUIPC` 的两个操作数必须分居
两侧,所以 **`imm_u` 一挪到 op2,`PC` 就必须挪到 op1** —— 问题 1 和问题 3 是同一件事。

数一下 mux 输入,发现代价是零:

| | 现状 | 改后 |
|---|---|---|
| op1 | rs1, **imm_u**, imm_z(3) | rs1, **PC**, imm_z(3) |
| op2 | rs2, imm_i, imm_s, **PC**(4) | rs2, imm_i, imm_s, **imm_u**(4) |

纯粹是重新贴标签。改完语义反而更整齐:**op1 = 被操作的值,op2 = 修饰量**(另一个
寄存器 / 立即数 / 移位量)。

移位在这个框架下自洽:`alu_shamt = alu_op2(4,0)`(`dpath.scala:172`),被移的值在 op1、
移多少在 op2。`SLLI` 的 shamt 来自 `imm_i`(在 op2)、`SLL` 的来自 `rs2`(在 op2),
立即数集中到 op2 之后它们还在 op2,**没有冲突**。

### 岔路:一个关于 don't care 的误判

这里我一度以为 `LUI` 可以写成 `OP1_X + ALU_ADD`,靠 `MuxCase` 的默认值让 op1 取 0。
查 `consts.scala` 发现不行:

```scala
val OP1_RS1 = 0.asUInt(2.W)
val OP1_IMU = 1.asUInt(2.W)
val OP1_IMZ = 2.asUInt(2.W)
val OP1_X   = 0.asUInt(2.W)     // ← 和 OP1_RS1 是同一个编码
```

**`X` 不是独立编码,是 `RS1` 的别名。** `MuxCase` 的默认分支永远走不到。这是为了省
mux 宽度:2 bit 刚好够 3 个真实来源,不必为"不关心"再留一个编码。

代价是 **op1 没有"零"这条路**,所以 `LUI` 只能靠 COPY 类操作。

副作用:`BEQ` 那行虽然写着 `OP1_X, OP2_X`,硬件上 `alu_op1` 实际是 `rs1_data`、
`alu_op2` 是 `rs2_data`,ALU 照样在算一个加法,只是结果没人要。**读代码时不要把 `X`
当成 0。**

---

## 第 2 个:一个 COPY 就够,但选哪个方向不对称

`imm_u` 挪到 op2 之后,`LUI` 需要 `ALU_COPY2`。那么自然的问题是:既然有了 COPY2,
还需要 COPY1 吗?

逻辑上不需要 —— 一个方向就够。但看谁在用 COPY1:

```
CSRRW / CSRRS / CSRRC    → OP1_RS1, OP2_X, ALU_COPY1     源是 rs1
CSRRWI / CSRRSI / CSRRCI → OP1_IMZ, OP2_X, ALU_COPY1     源是 imm_z
```

**要干掉 COPY1,就得把 `rs1` 和 `imm_z` 也接到 op2 上。** 而 `rs1` 必须留在 op1 —— 每
一条 R 型和 I 型指令都要它当第一操作数。于是 `rs1` 得**同时挂在两个 mux 上**。

三个方案摊平:

| 方案 | op1 输入 | op2 输入 | ALU 操作数 | 相对现状 |
|---|---:|---:|---:|---|
| **现状**(只有 COPY1) | 3 | 4 | 11 | — |
| COPY1 + COPY2 | 3 | 4 | **12** | 多一个 ALU 操作 |
| 只有 COPY2 | 2 | **6** | 11 | 多一路 32 位操作数 mux,`rs1` 双扇出 |

**每一种改法都比现状差。**

> **实测:错了。** 变体 A(表中第二行"COPY1 + COPY2")实测比 baseline **少 79 个 LUT
> (−6.5%),Fmax 高 2.5%**。这张表把"多一个 ALU 操作"当成成本,但生成的 Verilog 显示
> ALU 结果 mux 本来就是 `2^4 = 16` 项的数组,空槽填常量 —— **在译码空间用满之前,多一个
> 操作码接近免费**。而且"输入个数"根本不是 mux 代价的正确度量:mux 规模由选择信号位宽
> 决定,单路输入的代价则取决于其中有多少位是常量或与其它输入共享。

### 为什么现状不用付这个代价

因为 op1 那三路**全部身兼两职**:

| op1 输入 | 当普通操作数 | 当 COPY1 的源 |
|---|---|---|
| `rs1` | `ADD`/`SUB`/`SLL`… 的第一操作数 | `CSRRW` |
| `imm_u` | `AUIPC` 的加数 | `LUI` |
| `imm_z` | — | `CSRRWI` |

只有 `imm_z` 是专用的。**三路 mux 支撑了三条 COPY 路径,一个额外输入都没花。**

Sodor 把 COPY 路径完全寄生在已有的 mux 上。而 op2 那边 `rs2` 和 CSR 完全不搭界
(CSR 要的是 `rs1`),所以 copy 走 op2 搭不到便车。

> **COPY 应该从"本来就得存在的那条路"上走。** Sodor 选 COPY1 而不是 COPY2,不是
> 任意的。

### 补充:代价的位置比代价的大小更重要

"保留两个 COPY 会浪费资源"这个直觉方向对,但要看浪费在哪:

```
操作数 mux ──→ [加法器/移位器] ──→ 结果 mux ──→ wb
     ↑                                 ↑
  加宽这里,延迟穿过整个运算单元    加宽这里,只影响运算之后
```

`COPY2` 的输入 `alu_op2` 接在**结果 mux** 上;而把 `rs1` 挂到 op2 是加宽**操作数
mux**,在运算单元之前,延迟会把整条进位链往后推。

所以"保留两个 COPY"很可能**时序上反而更好**,虽然它多一个操作码。硬件里说"浪费资源"
之前,先问一句:浪费在关键路径上,还是浪费在旁边?

## 质疑接口:整个两难是可以绕开的

回头看 CSR 的写数据是从哪来的(`dpath.scala:199`):

```scala
csr.io.rw.wdata := alu_out
```

**这才是 `CSRRW` 必须占用一个 COPY 操作的根本原因。** ALU 被迫做一次"什么都不做"的
运算,只为了把 `rs1` 搬到 CSR 文件。

改成一条专用通路:

```scala
csr.io.rw.wdata := Mux(csr_use_imm, imm_z, rs1_data)
```

那 6 条 CSR 指令**完全不碰 ALU**,`alu_fun` 可以全填 `ALU_X`,`imm_z` 也能从 op1 mux
上摘掉。COPY 只剩 `LUI` 一个用户 —— 那时候用 COPY1 还是 COPY2 就真的随便了,最初的
直觉在那个设计下完全成立。

代价是一个专用的 2:1 32 位 mux;收益是把 CSR 从主运算通路上摘出去。这个取舍在流水线核
里更划算,因为 CSR 访问本来就要特殊处理(有副作用、需要串行化),走独立通路更干净。

> **实测:这是本篇最大的翻车。** 这个方案(变体 B)实测**多用 31 个 LUT(+2.5%),
> Fmax 低 2.5%** —— 面积和时序两项都输给原设计。
>
> 附带发现是好的:`inst(14)` 就能区分 CSR 的立即数形式和寄存器形式,所以**不需要新增
> 控制信号**,改动完全局限在 dpath 内。op1 也确实从 4 项数组塌缩成了更便宜的三元链。
> 但净效果仍然是变差,而我**至今无法定量解释这 31 个 LUT 从哪来**。
>
> 教训:这一节在整条推理链里是"最深刻的一步"——跳出局部约束去质疑上游接口。但**推理
> 的深度不保证结论的正确**。在单周期 RV32I 这个具体规模上,原设计恰好就是更优的。

## 方法论

这次探索走完了一个完整的循环:

1. 提出一个看起来更整齐的重排
2. 逐条指令验证 → 大部分没问题
3. 撞到一个例外(`CSRRW`)
4. 分析例外的两种解法,发现都要付费
5. **追问例外的成因**(CSR 写数据来自 `alu_out`),发现改动那里可以消除整个约束

**第 5 步是关键。** 前四步是"在给定接口下重排",第 5 步是"质疑接口本身"。真实的架构
工作大部分时间花在第 5 步 —— 一个看起来无解的局部约束,往往是上游某个设计决定的影子。

**但第 6 步才是决定性的:把它实现出来,量一量。**

这一整套推理漂亮、自洽,而且**两个定量结论都是错的**。纸面上数门电路能告诉你一个改动
*有没有*代价,但说不准代价的**符号和大小** —— 因为综合工具看到的是位级的常量传播和
共享,不是你脑子里那张框图。

两个附带结论:

- **译码表的各列不是独立的。** `op1_sel`、`op2_sel`、`alu_fun` 三列耦合,动一列另外
  两列就要还债。
- **ISA 边角会决定微架构。** `CSRRW` 这条特权指令,最后决定了通用数据通路上 mux 的
  形状。

## 动手验证

这几个改动范围都很小,而且可证伪 —— 51 个 ISA 测试全过才算数。

**改动 A:`imm_u` 与 `PC` 对调**(应当零代价)

1. `consts.scala`:`OP1_IMU` → `OP1_PC`,`OP2_PC` → `OP2_IMU`
2. `dpath.scala`:两个 `MuxCase` 里对应换线
3. `cpath.scala`:`AUIPC` 行改成 `OP1_PC, OP2_IMU`
4. ALU 增加 `ALU_COPY2 -> alu_op2`
5. `cpath.scala`:`LUI` 行改成 `OP1_X, OP2_IMU, ALU_COPY2`

**改动 B:把 CSR 写数据从 ALU 上摘下来**(消除约束)

1. `dpath.scala:199` 改成专用 mux
2. `cpath.scala`:6 条 CSR 指令的 `alu_fun` 改成 `ALU_X`
3. 从 op1 mux 上删掉 `imm_z`

验证:

```bash
cd ~/github/chipyard/sims/verilator
make CONFIG=Sodor1StageConfig run-asm-tests-fast    # 退出码 0 = 51 个全过
```

**这两个改动已经做完并量过了**,补丁在
[`tools/synth/variants/`](https://github.com/eecsmap/cpu-design-lab/tree/main/tools/synth/variants),
数据和方法学在
[measurements/2026-08-30-operand-mux-variants.md](https://github.com/eecsmap/cpu-design-lab/blob/main/measurements/2026-08-30-operand-mux-variants.md)。
三个变体都通过了全部 51 个 ISA 测试 —— **功能不对的话面积数字没有意义**。

顺带一提,预期中的"用面积换关键路径"取舍**根本没有出现**:两个变体都是面积和时序
同向变化,A 两项都好,B 两项都差。
